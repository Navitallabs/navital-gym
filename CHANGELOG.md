# Changelog

## v1.1 (grader tree id 1543b5103be5, 31 Oct 2026)
Verify with `git rev-parse v1.1.0:navital_gym` (first 12 characters). Every v1.1 row is graded by that one id. v1.1 changes grading code and some task data, so v1.1 scores are not comparable with v1.0.1 scores; the tables below show both.

### What changed
- **Trip.** A night in Nubra or Pangong now needs the Ladakh fee. It is one fee per trip, paid with any Nubra or Pangong visit marked `fee_paid: true` (the trip prompts are unchanged for this rule). Also: Tatkal Aadhaar OTP hand-off, general quota booking 1-60 days ahead with sold-out corridors, return city and origin stated in the prompts, `R-BUD` in exact arithmetic (a leg that is not a real service fails `R-BUD`, and `R-CONN` names the leg), `R-REST` counts an overnight arrival as travel on the arrival day, `R-ALT` allows no onward travel on the day you first reach Leh, tasks 027-030 and 054 drop an unstated diet parameter, 039 avoids Kaziranga, 050 needs a hotel with a lift.
- **UPI.** Mandate prompts (041-045) say that registration needs the owner's own UPI PIN. The oracle's refusal reasons follow the world's check order. Amounts are checked exactly (whole rupees compared as decimals, no float rounding). The action log is never truncated (over 2000 calls is a malformed submission).
- **Support.** `R-AMOUNT` checks exact amounts and, for Hindi and Hinglish replies, which figure the reply promises as the refund (more rupee spellings, unmarked decimals, breakdowns that add up). `R-PRIVACY` flags any address part, including the locality; a PIN leaking alone, and a house number after an address word ("flat 55", "मकान नंबर:55", "पता #55"). `R-LANG` has a reply-quality floor and whole-word Devanagari markers. Negative figures (a minus before the figure) are checked for the ₹, Rs and INR markers.
- **Form.** A PIN code written as a number is accepted.
- **Core.** A rule that raises is reported by name. `extract_json` ignores braces inside strings (no saved run changes). A tool error (e.g. a date overflow or a deeply nested call) is returned to the agent instead of crashing the run. `pass@1` uses first-run semantics. `verify_submission` needs an attempt and a transcript for every task.
- **Adapters.** For UPI, the verifiers adapter grades the action log the rollout executed, not the one the answer claims.
- **Export.** `leaderboard.json` carries no file-modified dates (`date` is null for our own runs) and appends the reasoning-effort setting to the model name.

### Known issues (to be fixed in v1.1.1)
- **R-AMOUNT (support).** Some ways of stating a refund are not checked yet: ranges joined by words ("₹1899 से लेकर 2500 तक", "between ₹1899 and 2500") check only the end next to the rupee sign; the spelling "rupaiya" is not recognised; a minus glued to the word before it ("रिफंड-₹1899") is read as a hyphen, and the minus check knows only the ₹, Rs and INR markers. For the experimental Tamil, Bengali and Marathi replies, and for a figure given in another role (such as a reference number), the rule checks which rupee figures appear, not which one the reply calls the refund. A number right after a suffix marker ("1899 रुपये 5 दिनों में") is read as a rupee figure, which can fail a correct reply. None of these spellings occurs in the saved v1.0.1 or v1.1 support replies. To be fixed in v1.1.1.

## v1.1 follow-ups noted for v1.2
- **Support `R-AMOUNT` role of the figure.** The refund figure is checked for presence, not role: a reply that gives it only as, say, a reference number still passes `R-AMOUNT` (`R-ACTIONS` checks the actual refund). A spaced dash ("- 1899 रुपये") is read as a separator, not a minus.
- **Assamese vs Bengali.** The experimental Bengali split is checked by script only, so an Assamese reply passes as Bengali.
- **Tool errors.** Since v1.1 a `ValueError` or arithmetic error inside a tool (e.g. a 9999-12-31 date) is returned to the agent as an error instead of crashing the run; a bug in our own tool code would therefore show up as an agent failure, not an errored task. v1.2 will separate the two.
- **UPI reason `over_daily_count`.** The UPI oracle now answers `insufficient_balance` and `over_daily_count` in the world's check order (balance and daily payment-count boundaries). `over_daily_count` will be listed in the UPI instructions in v1.2; the instructions are unchanged in v1.1 so that no UPI task prompt changes. No public task reaches either path.

## v1.0.1 (29 Oct 2026)
- **Reply language is now a hard rule on the Tamil, Bengali and Marathi support tasks.** In v1.0.0 `R-LANG` applied only to the 50 Hindi and Hinglish core tasks; the 26 experimental tasks were solved on state alone, so the built-in `english` baseline (right actions, English reply) solved 33% of the full 76-task split and a no-action agent could pass the "decline" tasks without writing in the customer's language. `R-LANG` is now in the rules of all 76 tasks (`tasks.jsonl`, `build_tasks.py`). Tamil and Bengali are checked by script; Marathi also needs two Marathi marker words (the same check as before, which was only reported, not scored). Scripted baselines at the new grader: oracle 76/76, `english` 0 (was 26 of 76), `refund_all` 0, `empty` 0, `noop_lang` 4 of 76 (3 of the 50 core, 1 of the 26 experimental); every non-oracle baseline is under 25% on the core, the experimental tasks and the full split. This is a grader change: new tree id, and every saved run was re-graded by replay (`scripts/regrade.py`, no model was called again). The rule: at least 70% of the reply's letters must be in the customer's script (Hindi, Marathi, Bengali, Tamil), so a reply in the right language that is heavily mixed with English words fails by design, as it already did on the Hindi core since v1.0.0. Support rows that include the experimental tasks can therefore score lower than in v1.0.0 wherever the reply is in the wrong language or mostly not in the native script. Effect on the published rows: only Sarvam-105B's support row changed pass@1 (full 76 tasks 0.43 -> 0.38; the 26 experimental tasks 0.58 -> 0.42). The 4 tasks had been solved on state alone: 2 replies in the wrong language (IN-SUP-073, a Hindi reply to a Marathi customer; IN-SUP-076, English) and 2 in the right language but only 47% in the native script (IN-SUP-062 Bengali, IN-SUP-070 Marathi, heavily mixed with English words), which fail the 70% rule by design. Claude Haiku 4.5, Claude Sonnet 5.5 and GPT-4o-mini keep the same pass@1; partial credit rose slightly on the Haiku, Sonnet and GPT-4o-mini support rows (and moved a little on Sarvam's) because `R-LANG` is now one more scored rule. Every other env's rows are unchanged.
- **Two Marathi reply lines reworded.** The scripted oracle's Marathi refund line (used for tasks IN-SUP-066 and IN-SUP-067) and its Marathi `decline_return` line each carried only one Marathi marker word and failed the Marathi check once it became hard. Both now carry two (`तुमच्या` in the refund line; `आम्ही ... आहोत` in the decline line). The meaning is the same; the lines were edited by hand, not re-run through the Sarvam back-translation check, and are still not native-reviewed. Customer prompts, worlds, tasks, decisions and the oracle logic did not change.
- **Length cut-off column.** RESULTS and `leaderboard.json` (new key `truncated_tasks`) now report how many tasks of a row ended because the model hit its output-token limit (`finish_reason: length`, `meta.truncated`). The first attempt hit the limit; the column counts only tasks that ended unsolved (the one format-repair retry is allowed, so a cut-off task it still solved is not counted: that is 1 task, Groq gpt-oss-20b easy GST). A reasoning model can spend its whole output limit (32,000 tokens for Sarvam) before writing an answer: the Sarvam trip row has 9 of 55 tasks cut off (all unsolved). This changes no score.
- **json_object footnote.** Run settings say `json_mode_on_final: true`, but for Sarvam the harness cannot send `response_format` on the final call (explained in `docs/RESULTS.md`). Documentation only.
- **Versions.** Package, citation and `navital_gym.__version__` are 1.0.1. Verify with `git rev-parse v1.0.1:navital_gym`.

- **Core:** `summarize()` reports `by_split` and `by_kind`; a well-formed empty answer earns no partial credit (the format gate is not scored); arriving in the city where a trip ends counts as visiting it.
